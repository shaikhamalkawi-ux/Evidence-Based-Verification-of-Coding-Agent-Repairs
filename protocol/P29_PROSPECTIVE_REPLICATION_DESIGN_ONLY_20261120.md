# P29 — Suggested prospective replication design ONLY (NOT YET PREREGISTERED)
Design date: 20 Nov 2026. This file is an internal plan and must not be represented as a prospective protocol until a task frame, inclusion rules, execution code, outcome definitions and immutable timestamped registration are sealed **before** future candidate outcomes become visible.

## Rationale
P28 identified strong prior art on benchmark validity and a tiny mixed-stage, post-reveal two-control sample. A full-length methodology claim would require genuinely new generalizable empirical evidence rather than polishing P27 figures.

## Minimal precommit design, without any fictional human coder
- Freeze a **new**, clearly non-overlapping source task frame, source dataset revision, source branch and sample-selection SHA before running agents. Preserve the original ten cases as **historical**, not an independent prospective test.
- Use an actual, separately attributable coding agent or logged API-run agent; capture authenticated job/actor identifiers, model/configuration and prompt hashes, source base SHA, patch SHA-256, timestamps, command/output logs and tool-call audit. Do not infer autonomous model identity from Git display names.
- Define one candidate stage (prefer first autonomous attempt) and one common task pipeline. Never combine first attempts with post-feedback revisions under an unqualified denominator.
- For every selected task, preregister an original-source no-code/neutral-control evaluator run on the **same pinned test set**, ideally with replicate controls or clock/dependency isolation as appropriate, including runner image digest and environment identity.
- Seal endpoint handling: **official strict resolved**, **F2P issue-test**, **P2P candidate-exclusive failed named IDs**, **systemic import/collection invalid**, **actor/source admission**; distinguish named test IDs from unique failure causes. Preserve raw official labels. Add gold/reference-patch validity checks if test/date drift suspected.
- Lock acceptance policies and HOLD reasons before independent task truth is seen; no posthoc re-thresholding. A no-accept policy has undefined accepted risk, not zero.
- Freeze analysis/uncertainty approach before test outcomes; report per-task counts, separate task and test denominators, acceptance coverage, logical endpoint-risk bounds, and attrition. No confidence intervals or superiority unless the sampling process, sample size and homogeneous design justify them.
- Ensure test suite does not silently import confidential hidden grader code or leak task answers to the agent. Keep any private benchmark source under appropriate licences and permission restrictions.
- Execute full standalone corruption controls: alter task ID, source base, test ID, status, candidate SHA, baseline SHA, actor ID and timing individually; tests must detect alteration.
- Archive exact input/output SHA manifests and reproducibility package with unmodified official benchmark results separate from posthoc analyses.
- Use AI-assisted evidence coding and cross-check only; **do not invent human annotators, human agreement coefficients or independent human approval**.

## Required GO gate before writing a high-claim journal manuscript
(1) Pre-outcome immutable registration; (2) real actor-linked executions; (3) multiple paired original controls; (4) independently reproducible all nine-or-more new task evidence; (5) stable endpoint validity; (6) credible novelty relative to ICSE 2026, October 2026 arXiv audit and upstream issue #100. This design does not claim these six gates have passed.

## Explicit invariants
P9–P27, MR30, strict original SWE-bench-Live labels and old 10-task denominator are untouched. This plan adds **zero** new executed tasks or agents and is NOT a result or an advance registration.
